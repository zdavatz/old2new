# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

old2new enhances old Da Vaz videos using Real-ESRGAN AI upscaling. There are two approaches depending on the environment:

1. **Local (macOS)**: `enhance.sh` — uses Real-ESRGAN ncnn-vulkan binary (Vulkan/Metal)
2. **Cloud GPU**: `enhance_gpu.py` — uses Real-ESRGAN Python package (PyTorch/CUDA)
3. **Google Cloud (one-command)**: `gcp_setup.sh` — creates instance, installs deps, runs enhancement
4. **Batch (vast.ai)**: `vast_batch.sh` — parallel upscaling of all 226 davaz.com videos on multiple RTX 4090 instances
5. **Batch (TensorDock)**: `tensordock_batch.sh` — SSH VMs with auto-sized disk, RTX 4090 instances

## Architecture

- **enhance.sh** — macOS script: YouTube URL or local file → detect hardware → benchmark → check disk → interactive menu → extract frames (ffmpeg) → upscale (Real-ESRGAN ncnn-vulkan) → reassemble (ffmpeg)
- **enhance_gpu.py** — Cloud GPU script: same pipeline but PyTorch/CUDA. Pre-flight check (GPU, CPU, RAM, disk, PCIe, software). Parallel frame extraction (up to 16 ffmpeg workers). Parallel I/O pipeline (threaded pre-read + async write). Auto-tiling based on VRAM. Supports `--job-name`. Uses `~/jobs/<name>/`.
- **gcp_setup.sh** — One-command Google Cloud setup: pre-checks video size → creates L4 GPU instance → installs deps → starts enhancement. Supports `status` with ETA.
- **vast_batch.sh** — vast.ai script. Supports: YouTube URL (single video), `test`, `launch N` (batch 226 videos on N instances). Also: `status`, `download`, `destroy`, `list`. Auto-detects HD → recommends 2x. Web dashboard via bore.pub tunnel.
- **runpod_launch.sh** — RunPod script (BROKEN — pods never start). Commands: `test`, `launch`, `status`, `ssh`, `download`, `destroy`, `destroy-all`, `list`.
- **tensordock_batch.sh** — TensorDock API SSH VMs. Auto-calculates disk from resolution x duration x scale. Auto-detects tiling risk → switches to RTX 5090 for HD. Commands: `test [VIDEO_ID]`, `launch N`, `status`, `ssh N`, `download`, `destroy`, `list`. Cloud-init installs all deps, disables unattended-upgrades (~3min vs ~12min boot). Deploys OAuth credentials via cloud-init write_files for auto YouTube upload + email. Default user `user`. Port forwarding SSH (22) and dashboard (8080).
- **youtube_upload.py** — Uploads enhanced video to YouTube (copies title + "Enhanced 4K" suffix), sends email to juerg@davaz.com via Gmail API. Requires `client_secret.json` + `youtube_token.json` (OAuth2 youtube.upload + gmail.send). For video IDs starting with dash, use `--video-id=-x_aIkSrXFw`. **YouTube API Quota**: 10,000 units/day (resets midnight Pacific = 07:00 UTC). ~150 units/upload → ~66 uploads/day. Monitor at [Google Cloud Console](https://console.cloud.google.com/apis/api/youtube.googleapis.com/quotas). `quotaExceeded` → MKVs stay for retry. `retry_uploads.sh` scans for unuploaded MKVs, scheduled via cron (`5 7 * * *`) or sleep-based timer.
- **youtube_upload_rs/** — Rust replacement for `youtube_upload.py`. Binary deployed as `~/youtube_upload`. Same functionality + appends to `~/upload_log.jsonl` + updates `timing.json`. Direct token refresh via Google OAuth2. Supports `--title` for custom upload titles (e.g. "Enhanced 4K v1" for brightness-corrected re-uploads). Built with `cargo build --release`, deployed via `deploy.sh update`.
- **tk_push_rs/** — TikTok video upload via Content Posting API. OAuth2 PKCE auth flow (`--auth`) with S256 hex-encoded SHA256 (TikTok deviates from RFC 7636 base64url). Local callback on port 8091, auto-kills stale listeners. Chunked upload (single chunk up to 64MB, 10MB for larger) with progress, status polling. Sandbox/unaudited apps must use `--privacy self` (uses inbox/draft endpoint). Usage: `tk_push --auth` (first time), `tk_push video.mp4 --title "Title" [--privacy self]`. Credentials in `tiktok_credentials.json`, token in `tiktok_token.json`. Writes PID to `~/tk_push.pid`.
- **create_short_rs/** — Rust binary `create_short` for extracting a segment from a YouTube video and re-uploading as a new video. Pipeline: yt-dlp `--download-sections "*START-END" --force-keyframes-at-cuts -f bestvideo[height<=2160]+bestaudio/best --merge-output-format mp4` → upload via Google YouTube API. Reuses auth/upload patterns from `youtube_upload_rs` (PythonToken refresh against `youtube_token.json`). Required: `--start`, `--end`, `--title`, `--description`. Optional: `--privacy {public|unlisted|private}` (default public), `--format`, `--output`, `--keep` (don't delete after upload), `--dry-run`. Default output `/tmp/create_short/<sanitized-title>_<start>-<end>.mp4`. Usage: `create_short <url-or-id> -s 12:44 -e 13:14 -t "title" -d "description"`. Run from project dir so `client_secret.json` + `youtube_token.json` are found. Description on the new video is auto-suffixed with `\n\nOriginal: <url> (<start>-<end>)` linking back to the source video.
- **create_shorts_gui/** — Cross-platform desktop GUI (eframe/egui) wrapping the `create_short` pipeline for non-CLI users (built so Jürg can self-serve): Preview/edit a YouTube segment (cut out sections, burn-in title overlay, freeze-frame fade in/out, time-stretch), upload to YouTube, export a PDF of latest shorts, and share to WhatsApp / davaz.com / LinkedIn / X. In-window mpv video preview with cut-range overlay; segment cache; OAuth via user's own Google client. **Full architecture, pipeline stages, and per-version changelog now live in `create_shorts_gui/CLAUDE.md`** (loaded automatically when working under that directory). Build: `cd create_shorts_gui && cargo build --release`. Run: `./target/release/create_shorts_gui`. **Release**: tag `create-shorts-vX.Y.Z` triggers `.github/workflows/create-shorts-release.yml` (Linux tar.gz, Windows .exe zip, macOS notarized universal `.app` DMG; bundle ID `com.ywesee.createshorts`).
- **li_push_rs/** — LinkedIn video upload via Videos API + Posts API. OAuth2 auth flow (`--auth`) with OpenID Connect for person ID extraction from JWT id_token. Local callback on port 8092. 4-step upload: initialize → chunked upload (4MB parts with ETags) → finalize → create post. Supports YouTube URL or video ID as input — auto-downloads via yt-dlp with title/description. Pre-checks duration (max 30 min) and filesize (max 500MB). `--low-quality` flag for 1080p fallback when video exceeds 500MB. Shows post URL after publish. Upload log in `~/li_push_log.jsonl` prevents duplicate uploads. `--random-short` picks a random unuploaded short from `csv/davaz_enhanced_list.csv`. `--list` shows all previous uploads. Usage: `li_push --auth`, `li_push video.mp4 --title "Title"`, `li_push YOUTUBE_ID`, `li_push "https://youtube.com/..." --low-quality`, `li_push --random-short`, `li_push --list`. Credentials in `linkedin_credentials.json` (`{"client_id": "...", "client_secret": "..."}`, gitignored), token in `linkedin_token.json`. Writes PID to `~/li_push.pid`. App registered at `developer.linkedin.com/apps` with redirect URI `http://localhost:8092/callback` and products *Sign In with LinkedIn using OpenID Connect* + *Share on LinkedIn* (scopes `openid profile w_member_social`). **X / Twitter posting (`src/twitter.rs`)**: `--twitter` posts to X *in addition to* LinkedIn, `--twitter-only` posts to X only (skips LinkedIn). Auth is a one-time OAuth 2.0 Authorization-Code-with-PKCE browser flow (`--auth-twitter`) reusing the same port-8092 callback, scopes `tweet.read tweet.write users.read media.write offline.access`; confidential client (client_secret present) → HTTP Basic on the token exchange + refresh. Token in `twitter_token.json`, app creds in `twitter_credentials.json` (`{"client_id","client_secret"}`, both gitignored). **Posts native video (with frame+link fallback)**: uses X's v2 *chunked* media upload — `POST {api.x.com}/2/media/upload/initialize` (JSON `{media_category:"tweet_video",media_type:"video/mp4",total_bytes}`, NO `command` field — that's the retired v1.1 protocol) → `POST /2/media/upload/{id}/append` (multipart `segment_index`+`media`, 4 MiB segments) → `POST /2/media/upload/{id}/finalize` → poll `GET /2/media/upload?command=STATUS&media_id=` until `processing_info.state==succeeded`. **Critical**: X rejects video above 1920×1200 (the Da Vaz sources are Enhanced 4K) and is codec-picky, so `post_to_twitter` first ffmpeg-transcodes to an X-friendly spec (H.264 `-profile high` / `yuv420p`, longest edge ≤1280 via `scale='min(1280,iw)':'min(1280,ih)':force_original_aspect_ratio=decrease` + even-dim `scale=trunc(iw/2)*2:trunc(ih/2)*2`, 30 fps, AAC 128k, `+faststart`); without the downscale, processing fails at 99% with `{"state":"failed"}`. The earlier belief that native video was impossible was a red herring — the failure was the bare `/2/media/upload` endpoint (which only accepts the single-shot image schema, `tweet_image`/image mime) plus 4K resolution, not an app-tier limit. If native upload still errors, it falls back to extracting a JPEG frame (1s in, fallback first frame), uploading via the single-shot `/2/media/upload` (`media_category=tweet_image`), and tweeting `title\n<youtube-url>`. Tweet creation is `POST /2/tweets` with `media.media_ids`, caption capped to 280 chars. **Original-video link**: every post (LinkedIn commentary *and* the X caption) links the original pre-enhancement video — sourced from the CSV `Original` column (field 1) for `--random-short`, else parsed from the short's YouTube description via `extract_original_link` (prefers a line mentioning "original", else the first YouTube URL that isn't the short itself). NB the Enhanced 4K shorts have *empty* descriptions, so the CSV is the real source for `--random-short`; the description path only kicks in for direct-URL inputs that carry an `Original: <url>` line (e.g. create_short output). When no original is found, the X caption falls back to linking the short itself. Separate X dedup log at `~/li_push_twitter_log.jsonl` (youtube_id, title, tweet_url, timestamp); `--random-short --twitter-only` dedups against it independently of the LinkedIn log. X app registered at `developer.x.com` with the same `http://localhost:8092/callback` redirect, type *Web App (confidential)*, app permissions *Read and write*. Usage: `li_push --auth-twitter` (first time), `li_push --random-short --twitter-only`, `li_push video.mp4 --twitter` (both). **Post analytics (`--stats`, `--stats-limit N`)**: reads view/engagement counts for previously posted videos from the `memberCreatorPostAnalytics` API (`GET /rest/memberCreatorPostAnalytics?q=entity&entity=(ugc:<encoded ugcPost urn>)&queryType=<METRIC>&aggregation=TOTAL`, plus `q=me` for the lifetime total), pinned to `LINKEDIN_ANALYTICS_VERSION=202608` — separate from `LINKEDIN_VERSION` (202603) used by the upload path, since 202604+ returns a flat `metricType` and adds save/click/follower metrics. Metrics: IMPRESSION (= "views"), MEMBERS_REACHED (unique viewers), REACTION, COMMENT; also RESHARE/POST_SAVE/LINK_CLICKS/FOLLOWER_GAINED_FROM_CONTENT/PROFILE_VIEW_FROM_CONTENT. All 132 posts already carry their `post_id` URN in `~/li_push_log.jsonl`, so no backfill is needed. **BLOCKED as of 2026-08-20**: the required `r_member_postAnalytics` scope is *not* self-serve — it is not in the app's Products tab, and requesting it in the auth URL fails the whole flow with `unauthorized_scope_error` ("Scope ... is not authorized for your application"), which is why `auth_flow()` deliberately does NOT ask for it; LinkedIn grants it only to applications approved via its Member Post Analytics form (rolled out July 2025 to vendors like Hootsuite/Buffer/Sprinklr). Re-add the scope to the auth URL only after approval. Until then per-post numbers exist only in LinkedIn's UI. **Download signed-out — cookies are the trap**: `--cookies-from-browser` is opt-in and should normally stay off. Sending cookies (a) makes YouTube meter the HD byte allowance against the *session*, so the download 403s partway through, and (b) makes yt-dlp >= 2026.08.19 skip the player clients that still serve HD, leaving only storyboards. Verified 2026-08-20 on the same video minutes apart: signed-in stalled at ~9.6 MB every time across many attempts, signed-out completed the full 13.98 MB VP9 stream first try. The flag remains for the case where a video genuinely needs auth (private/age-gated), at the cost of the cap. **HD formats gated behind a PO token**: the free clients need a GVS PO token (SABR) and otherwise serve nothing usable (`web`=images-only, `tv`=SABR-only, else 360p) — the bgutil provider covers this and yt-dlp's *default* clients pick it up on their own, so no `player_client` override is wanted. Fix = the [bgutil PO-token provider](https://github.com/Brainicism/bgutil-ytdlp-pot-provider) so the **`mweb`** client can present a PO token and stream un-throttled HD (`mweb` succeeds where every other client fails — `web`=images-only, `tv`=SABR-only). `li_push` auto-detects the provider (checks `~/bgutil-ytdlp-pot-provider/server/build/generate_once.js` at the plugin's default `server_home`) and, when present, adds `--extractor-args "youtube:player_client=mweb"` to the download; absent (cloud instances, Jürg's box) it falls back to yt-dlp defaults so nothing breaks. One-time setup (see README "YouTube 403 bot-detection & the PO-token provider"): `pip3 install -U --target ~/.config/yt-dlp/plugins/bgutil-pot bgutil-ytdlp-pot-provider` + clone `bgutil-ytdlp-pot-provider` tag 1.3.1 to `~/bgutil-ytdlp-pot-provider` and `cd server && npm ci && npx tsc` (plugin & server versions must match; script mode = no daemon, needs Node + deno). NB the PO token unlocks the HD *formats* but does not lift the byte allowance below. **Per-IP byte allowance (since ~Aug 2026)**: YouTube 403s a download the instant it exceeds a per-IP byte budget. Measured 2026-08-20: ~19.5 MB per stream on a rested IP, halving to ~9.6 MB after a burst of rapid retries, recovering only with idle time. It is a wall, not a throttle — `--http-chunk-size` (1M/2M/5M/10M), `--limit-rate`, `--retries` and `--continue` all die at the *identical byte offset* (proven: same video 403'd at 19.57 MB at 18 MiB/s and 19.52 MB at 2 MiB/s), and a Range request past the allowance is refused outright, so resume-across-sessions cannot work. Upstream calls it [an external issue](https://github.com/yt-dlp/yt-dlp/issues/17368), closed "not planned". Mitigation = **ask for fewer bytes**: the format string prefers **VP9 (webm)** over AVC — same 1080p in ~half the size (18.5 MB vs 36.2 MB) — capped at 1080p since LinkedIn tops out there and `post_to_twitter` downscales to ≤1280 anyway, so higher renditions only spend bytes both platforms discard. `--low-quality` now means VP9 ≤720p. LinkedIn expects H.264, so `ensure_h264` re-encodes a VP9 download locally (ffprobe check → libx264 CRF 18 `+faststart`; skipped when already h264 or when ffprobe is missing) — a codec swap at unchanged resolution, not a quality drop. **The allowance is per-session, so signing out is the actual fix** — see the cookie note above. The idle-for-hours advice only applies if you are stuck sending cookies; signed-out downloads were never capped. **Use yt-dlp >= 2026.08.19** (it drops the rate-limited `android_vr` from the defaults). Homebrew still ships 2026.7.4, so install the current one with `pipx install --backend pip yt-dlp` — `~/.local/bin` precedes `/opt/homebrew/bin`, so it shadows brew's; roll back with `pipx uninstall yt-dlp`. Never `brew uninstall yt-dlp`: **mpv depends on it**, and create_shorts_gui uses mpv for its preview. Beware a misleading A/B here — testing 2026.08.19 *with* cookies makes it look broken (storyboards only, or "The page needs to be reloaded") while old+`mweb` still works, which invites the wrong conclusion that the new release is a regression. It is not; drop the cookies and the defaults work.
- **yt_export.py** — Exports our own YouTube uploads via Google's [Data Portability API](https://developers.google.com/data-portability), so posting to LinkedIn/X can read local files instead of fighting YouTube's per-IP download byte cap (see the li_push_rs bullet). Returns the **original uploaded file**, not a transcode. NB the YouTube *Data* API v3 has no download endpoint at all — not even for videos you own — so this is the only programmatic route. Stdlib-only (no pip deps), loopback OAuth on port **8093** (8091=tk_push, 8092=li_push). Flow: `portabilityArchive:initiate` (body `{"resources":["youtube.public_videos"]}`) → poll `archiveJobs/{id}/portabilityArchiveState` until `state==COMPLETE` → download the signed Cloud Storage `urls`. Commands: `--auth`, `--initiate`, `--poll`, `--download`, `--reset`, `--job-id`, `--resources`, `--outdir`; bare invocation runs initiate+poll+download into `exports/`. Resource groups map 1:1 to scopes (`youtube.public_videos` → `https://www.googleapis.com/auth/dataportability.youtube.public_videos`); also `youtube.unlisted_videos` / `youtube.private_videos`. Credentials in `client_secret_dataportability.json` (Desktop-app client), token in `dataportability_token.json`, job state + signed URLs in `yt_export_state.json` (all gitignored — the signed URLs are themselves access grants). **Gotchas**: available only in ~30 countries (EEA/UK/**Switzerland** — we qualify); export covers whichever account authorizes, so sign in as the channel owner (@gozipa = Enhanced 4K shorts, @jdavatz = originals); job must be initiated within 24h of auth; jobs run minutes→7 days (script is resumable, Ctrl-C safe); signed URLs expire after 6h (re-`--poll` to mint fresh ones) though data lives 14 days; one-time access leaves scopes exhausted until `--reset` (Google auto-resets 14 days after first initiate); it is bulk per-account, not per-video. Requires enabling the Data Portability API in the Cloud project and adding the owner as a test user (the `dataportability.*` scopes are sensitive, so an unverified app only works for test users).

- **li_stats.py** — Joins LinkedIn's analytics export onto `~/li_push_log.jsonl` to give per-video reach. Needed because the `memberCreatorPostAnalytics` API is gated behind an approval-only scope (see the li_push_rs bullet), while the UI export is available to anyone with Creator Mode on. Export from [Post analytics](https://www.linkedin.com/analytics/creator/content/) → set the **date range on the page first** (the Export button follows the page's active range — a range chosen anywhere else is silently ignored; verify via the filename, e.g. `AggregateAnalytics_..._2025-08-21_2026-08-20.xlsx`) → Export. Usage: `./li_stats.py <xlsx> [--csv out.csv] [--sheet TOP-BEITRÄGE]`. Stdlib only — an .xlsx is a zip of XML, parsed via `zipfile` + `ElementTree`, reading cells by their `r` reference because empty cells are omitted. The join is **exact, not fuzzy**: the export's slug URLs embed `ugcPost-<id>`, the same id logged as `post_id`. The top-posts sheet holds several independently ranked blocks side by side (Engagement, Impressions), each `URL | date | value`, located by header text; a metric missing from a block prints `-` rather than `0`, since "not in that ranked list" is not "nobody did this". **Limits**: the sheet is capped at **50 posts**, and a short date range badly misleads — a 7-day export shows only that week's *incremental* impressions, so year-old posts read as 1–2 views and the profile looks dead; over 365 days the same posts median ~99. - **deploy.sh** — Deploys videos to cloud GPU instances. Modes: `<ids>` (auto), `new <ids>`, `--instance <ID> <ids>`, `--plan <ids>`, `update <instance_id>` (full redeploy + restart), `update-soft <id>` (upload as .new without restart), `swap-binary <id> <name>` (swap ONE binary, restart only that process — safe during ffmpeg/upscaling), `restart <id> <process>` (restart process without uploading binaries — safe, no disk risk), `destroy <instance_id>`. Options: `--single`/`--multi`, `--vastai`/`--tensordock`. **Safe update workflow**: `swap-binary` for binary updates, `restart` for process restarts without uploading. `status_server`, `gpu_scheduler`, `preparer`, and `youtube_upload` auto-restart after swap; other binaries (`enhance`, `frame_gap_check`, `rebalance_calc`) are replaced and used on next invocation. New instances use `restart.sh` (not `multi_gpu_queue.sh`). Enter key defaults to continue (not destroy). CPU verification: vast.ai boost clock != actual (searches `cpu_ghz>=4.0` for 5090, verifies via SSH). Blacklists bad machines to `blacklist_machines.txt`. **glibc pre-check**: both `deploy` and `update` verify remote glibc version before uploading binaries (need >=2.39 for slim, >=2.35 for compat). Aborts early if incompatible — prevents deploying binaries that fail with "GLIBC not found".
- **restart.sh** — Restarts all services: kills old processes (via PID files), replaces `.new` binaries, restores `.processing` queue files, starts preparer + gpu_scheduler + youtube_upload --watch + status_server. Each daemon writes PID to `/root/<name>.pid`. Usage: `./restart.sh [NUM_GPUS]`.
- **3-process architecture** — JSON is the contract. `deploy.sh` uploads `<yt-id>.json` to `~/json/`, triggering the pipeline:
  - **preparer** (Rust) — Polls `~/json/*.json`. Downloads video via yt-dlp, extracts frames via ffmpeg → `~/jobs/<yt-id>/frames_in/`. Writes `total_frames` to JSON when done.
  - **gpu_scheduler** (Rust) — Polls `~/jobs/<yt-id>/frames_in/`. Only starts when `total_frames` is present in JSON (preparer finished). Distributes GPUs proportionally, runs `upscale.py` with smart segment splitting (by actual missing frames), reassembles with ffmpeg + brightness matching. Writes `confirmed_frames_out` + `output_mkv` to JSON when done. Usage: `./gpu_scheduler [NUM_GPUS]`.
  - **youtube_upload --watch** (Rust) — Polls `~/jobs/<yt-id>/`. Only uploads when `confirmed_frames_out` is present in JSON (gpu_scheduler finished). Writes `.uploaded` lock file. Sends email to juerg@davaz.com. Also works in single mode: `youtube_upload <file> --video-id=<id>`.
  - No process starts before the previous has confirmed via JSON. Frame count verification gate before reassembly prevents corrupt uploads.
- **multi_gpu_queue.sh** — Legacy Bash queue processor (fallback if `gpu_scheduler` binary not available). Queue from `~/json/*.json`. Atomic pick via flock. 1 GPU per video only — no proportional distribution.
- **enhance.sh** (cloud version) — Bash orchestrator replacing enhance_gpu.py. Usage: `./enhance.sh <youtube-url> <scale> [--job-name <title>] [--gpu N]`. Also: `./enhance.sh done <json-path>`. Phases: parse args → job_meta.json → pre-flight → download → extract → upscale.py → frame gap check → reassemble → black frame check (optional, `CHECK_BLACK=0`) → upload → cleanup. `--gpu N` sets CUDA_VISIBLE_DEVICES. Upload uses `$HOME/youtube_upload` Rust binary (falls back to Python). `job_meta.json` written via `sys.argv` for special chars. PATH includes `/opt/venv/bin` and `/opt/conda/bin`.
- **upscale.py** — Minimal Python (~100 lines), ONLY Real-ESRGAN upscaling. Usage: `python3 upscale.py <frames_in> <frames_out> <scale> [--tile N] [--gpu-id N]`. Auto-tiling (tile=512 for >1.6 MP), deletes input frames in single-GPU mode (keeps last 10). In segment-split mode (`--end > 0`), inputs NOT deleted (shared dir). `--gpu-id N` creates GPU-specific tmp files (`frame_XXXXX.tmp.gpuN.png`) to avoid collisions when multiple GPUs write to the same frames_out dir. Startup cleanup only removes own GPU's tmp files. **Important**: tmp files must use `.tmp.png` (not `.png.tmp`) — OpenCV determines format from extension.
- **pimp_brightness.sh** — End-to-end brightness correction: download from YouTube → adjust segment → re-upload. Only re-encodes the affected segment (gamma correction), stream-copies the rest. Usage: `./pimp_brightness.sh <youtube-url> <start> <end> <percent> [--suffix v1] [--title "Custom Title"]`. Percent: `-25` = 25% darker, `+30` = 30% brighter. `--suffix v2` replaces any existing "(Enhanced 4K ...)" suffix → "Enhanced 4K v2". Uploads via Rust `youtube_upload` binary, sends email to juerg@davaz.com.

## Key Details

- Local: ncnn-vulkan uses Vulkan (Apple Silicon via MoltenVK). Cloud: ncnn-vulkan does NOT work in Docker (no Vulkan driver, falls back to CPU at 0.005 fps). **Always use PyTorch/CUDA for cloud.**
- Pre-flight validates: GPU CUDA arch, PyTorch/CUDA versions, CPU benchmark, RAM, disk + I/O, PCIe, ffmpeg, package versions.
- Pre-download disk check via `yt-dlp --dump-json` (no download) to estimate needs. Aborts if insufficient.
- CPU/disk impact: 4 vCPUs + 624 MB/s = 2.6 fps vs 16 vCPUs + 1207 MB/s NVMe = 7.0 fps (same RTX 4090). Always request 16+ vCPUs and NVMe >=1000 MB/s.
- CPU single-core matters: Xeon Phi 1.4GHz = 4x slower than EPYC 2.25GHz with same GPU. cv2.imread/imwrite bottlenecks on per-core speed.
- **RTX 5090 HD CPU benchmarks** (1920x1200, 2x, tile=512): Xeon Gold 6530 @ 0.9 GHz = ~0.1 fps (GPU idle!), Xeon 8481C @ 2.0 GHz = 0.3-0.4 fps, Ryzen 9 7950X @ 5.9 GHz = 0.5 fps, Threadripper PRO 7975WX @ 8.2 GHz = 0.5 fps, **Ryzen 9 9950X = 0.5 fps/GPU (best)**, Threadripper PRO 9975WX = 0.5 fps/GPU (slower than 9950X despite 64 cores — 4 CCDs = higher Infinity Fabric latency). Core count doesn't matter (16 cores sufficient), single-core speed + memory latency matters. **Min 3 GHz for RTX 5090 HD, ideal 5+ GHz.**
- RTX 5090 (Blackwell, sm_120) needs PyTorch 2.6+ / CUDA 12.8. Patch basicsr: `sed -i 's/functional_tensor/functional/' .../degradations.py`. Suppress tile spam: `sed -i "s/print(f'.*Tile/pass  # /" .../utils.py`. PyTorch 2.10 = no speedup over 2.7.
- **Docker images** — **always use slim image as default**. All deps pre-installed = no pip, no patching. Saves 5-8 min/instance.
  - `ghcr.io/zdavatz/realesrgan-benchmark:latest` — **slim ~4.5GB, USE THIS** (PyTorch 2.10 + CUDA 12.8 + Real-ESRGAN + ffmpeg + gcc). Requires driver >=570.
  - `ghcr.io/zdavatz/realesrgan-benchmark-compat:latest` — **compat ~4.5GB** (PyTorch 2.1 + CUDA 12.1 + pre-built Rust binaries for glibc 2.35). For older drivers (>=530). `deploy.sh` auto-selects based on driver version.
  - `ghcr.io/zdavatz/realesrgan-benchmark-full:latest` — full ~8GB (+ TensorRT + ONNX). Only for benchmarks.
  - `ghcr.io/zdavatz/realesrgan-ncnn-vulkan:latest` — ncnn-vulkan (reference only, doesn't work on cloud)
  - Built from `nvidia/cuda:12.8.0-runtime-ubuntu24.04` (not `base` — base lacks CUDA runtime). Compat from `nvidia/cuda:12.1.1-runtime-ubuntu22.04`.
- Processing is resumable: checks existing output. **Fast resume**: existing frames → skip preflight/download/extraction → straight to upscaling.
- `realesrgan-x4plus` model for both 2x and 4x (general-purpose, best for real-world content)
- GFPGAN DISABLED — hallucinates facial features. Not suitable for documentary footage.
- Reassembly: libx264, CRF 18, `-preset medium`. **Auto brightness matching**: samples 10 frames, compares brightness, applies gamma correction. `-preset slow` abandoned (identical quality at CRF 18, YouTube re-encodes anyway, 2x slower).
- Parallel frame extraction (up to 16 ffmpeg workers).
- **Auto-tiling**: RTX 4090/5090 safe up to 1.6 MP without tiling. Above 1.6 MP → tile=512 (always, regardless of VRAM). L40S/A6000 (48GB) up to 2.0 MP, 80GB+ up to 4.0 MP. Tiling **faster** for high-res: 1920x1200 tile=512 = 0.56 fps vs no-tile = 0.13 fps (RealESRGAN processes at 4x internally). **Do NOT increase tile size** — larger tiles use more VRAM but are slower (see tile size benchmark).
- GPU power matters: RTX Pro 6000 Max-Q 300W = 0.44 fps, RTX 5090 575W = 0.56 fps, RTX Pro 6000 S 600W = 0.62 fps. Pre-flight warns <400W for >30GB VRAM.
- Two GPU profiles: **SD-4x** (RTX 4090, 24GB, ≤1.6 MP, 7.0 fps, $0.50/hr) and **HD-2x** (RTX 5090, 32GB, 0.5-1.7 fps, $0.69/hr).
- **Datacenter GPUs NOT suitable** (except GH200): RTX Pro 6000 S = 0.6 fps/$3.41, B200 = 0.57 fps/$3.13, H100 = 0.46 fps/$1.90, L40S = 0.3 fps, A100 = 0.07 fps. No-tile always slower than tile=512.
- **GH200 Grace Hopper FASTEST single-GPU**: 0.74 fps at $2.26/hr (RunCrate). ARM64 — no x86 Docker. Not cost-effective vs RTX 5090 ($0.30-0.76/hr at 0.51 fps).
- **Multi-GPU scales linearly**: 4x RTX 5090 = 1.47 fps combined ($1.35/hr). Each GPU runs own process via CUDA_VISIBLE_DEVICES.
- **Multi-GPU queue**: shared queue with `flock` for atomic access. Avoids batch-of-N anti-pattern (GPUs idle waiting for slowest).
- **OOM-Kill recovery**: exit code > 128 = signal → retry same video after 60s (not skip). Max 3 retries. Normal failures (exit 1) skip.
- **Resume worker monitor** (`resume_workers.sh`): checks every 30s, uses PID-files per GPU. Do NOT use `/proc/$pid/environ` (race condition).
- **Don't let ffmpeg block GPU**: start next video on free GPU while ffmpeg reassembles on another.
- **Disk estimates use peak, not sum**: `max(input, output)` because upscale.py deletes inputs during upscaling. Warns when single video >60% of total disk.
- **Resume-aware disk check**: accounts for existing frames on resume. Existing frames_in counted as reclaimable.
- **Clean already-upscaled frames_in**: on constrained disks, delete redundant frames_in with corresponding frames_out.
- **Multi-GPU segment splitting**: `enhance.sh` splits frames across GPUs, runs `upscale.py --start N --end M`. Linear speedup. Deploy: `./deploy.sh --multi-one [N] <video_id>`.
- **Dynamic GPU joining**: idle GPU auto-joins remaining video by taking tail segment.
- **Rebalance**: `./deploy.sh rebalance <instance_id>` redistributes frames across all GPUs. Runs via nohup.
- **Multi-GPU disk sizing**: 500GB / 4 GPUs = 125GB each. 1920x1200 2x: max ~5min/video. 960x720 2x: max ~17min.
- **yt-dlp JS challenge** (since ~March 2026): requires `--remote-components ejs:github` for deno JS solver. Without it: "This video is not available". Slim Docker image includes deno.
- **Watchdog**: checks every 60s if enhance_gpu.py is running, restarts if not (resumable).
- **RTX 5090 optimization**: tile=512 optimal, FP16 67% faster than FP32 (already used), tile_pad=0 = 7% but risks artifacts, torch.compile() incompatible. GPU draws only 208W/575W at 1920x1200 — framework/CPU-limited. Per-res fps: SD 640x480 = 3.27 fps (340W), HD 960x720 = 1.47 fps (281W), HD 1920x1200 = 0.44 fps (208W). **Tile size benchmark** (RTX 5090, 1920x1200 2x): tile=512 = 0.4 fps (6.5GB VRAM), tile=768 = 0.3 fps (22GB), tile=1024 = 0.2 fps (29.7GB). Larger tiles use more VRAM but are slower — 4x internal tensors exceed GPU L2 cache. **Do NOT try**: ONNX Runtime CUDA/TensorRT (fails on Blackwell sm_120, TRT recompiles engine per tile size), Python threading/prefetch (GIL blocks, slower than sequential), larger tiles (cache thrashing). Sequential Python tile=512 is the proven optimum — only multi-GPU scaling helps.
- **status_server_rs/** — Rust status server binary `~/status_server` (~1.5 MB). Auto-scans `~/jobs/` + `~/json/`. 7 phases: downloading, extracting, upscaling, assembling, uploading, paused, done. Per-phase progress with fps, frame counts, ffmpeg speed, upload %, download %. Reads titles from `json/{id}.json`. Endpoints: `/` (HTML), `/api/status` (JSON), `/compare/{title}`, `/frames/{title}/{dir}/{file}`, `/download/{title}`. **GLIBC**: cross-compiled binary needs glibc 2.39. Slim image works; compat image has pre-built binaries for glibc 2.35; older images need on-server build. `restart.sh` auto-falls back to Docker image binary (`/usr/local/bin/`) if deployed binary has glibc issues.
- **SSH nohup detach**: use `sudo bash -c "cd /root && nohup cmd >> log 2>&1 &"` — `bash -c` wrapper ensures proper detach from SSH session.
- Instance metadata in `~/instance_meta.json` (label, location, cost_per_hr, provider, instance_id) — shown in dashboard.
