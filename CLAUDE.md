# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

old2new enhances old Da Vaz videos using Real-ESRGAN AI upscaling. There are two approaches depending on the environment:

1. **Local (macOS)**: `enhance.sh` — uses Real-ESRGAN ncnn-vulkan binary (Vulkan/Metal)
2. **Cloud GPU**: `enhance_gpu.py` — uses Real-ESRGAN Python package (PyTorch/CUDA)
3. **Google Cloud (one-command)**: `gcp_setup.sh` — creates instance, installs deps, runs enhancement
4. **Batch (vast.ai)**: `vast_batch.sh` — parallel upscaling of all 226 davaz.com videos on multiple RTX 4090 instances
5. **Batch (TensorDock)**: `tensordock_batch.sh` — SSH VMs with auto-sized disk, RTX 4090 instances

## Architecture

- **enhance.sh** — macOS script: YouTube URL or local file → detect hardware → benchmark → check disk → interactive menu → extract frames (ffmpeg) → upscale (Real-ESRGAN ncnn-vulkan) → reassemble (ffmpeg)
- **enhance_gpu.py** — Cloud GPU script: same pipeline but PyTorch/CUDA. Pre-flight check (GPU, CPU, RAM, disk, PCIe, software). Parallel frame extraction (up to 16 ffmpeg workers). Parallel I/O pipeline (threaded pre-read + async write). Auto-tiling based on VRAM. Supports `--job-name`. Uses `~/jobs/<name>/`.
- **gcp_setup.sh** — One-command Google Cloud setup: pre-checks video size → creates L4 GPU instance → installs deps → starts enhancement. Supports `status` with ETA.
- **vast_batch.sh** — vast.ai script. Supports: YouTube URL (single video), `test`, `launch N` (batch 226 videos on N instances). Also: `status`, `download`, `destroy`, `list`. Auto-detects HD → recommends 2x. Web dashboard via bore.pub tunnel.
- **runpod_launch.sh** — RunPod script (BROKEN — pods never start). Commands: `test`, `launch`, `status`, `ssh`, `download`, `destroy`, `destroy-all`, `list`.
- **tensordock_batch.sh** — TensorDock API SSH VMs. Auto-calculates disk from resolution x duration x scale. Auto-detects tiling risk → switches to RTX 5090 for HD. Commands: `test [VIDEO_ID]`, `launch N`, `status`, `ssh N`, `download`, `destroy`, `list`. Cloud-init installs all deps, disables unattended-upgrades (~3min vs ~12min boot). Deploys OAuth credentials via cloud-init write_files for auto YouTube upload + email. Default user `user`. Port forwarding SSH (22) and dashboard (8080).
- **youtube_upload.py** — Uploads enhanced video to YouTube (copies title + "Enhanced 4K" suffix), sends email to juerg@davaz.com via Gmail API. Requires `client_secret.json` + `youtube_token.json` (OAuth2 youtube.upload + gmail.send). For video IDs starting with dash, use `--video-id=-x_aIkSrXFw`. **YouTube API Quota**: 10,000 units/day (resets midnight Pacific = 07:00 UTC). ~150 units/upload → ~66 uploads/day. Monitor at [Google Cloud Console](https://console.cloud.google.com/apis/api/youtube.googleapis.com/quotas). `quotaExceeded` → MKVs stay for retry. `retry_uploads.sh` scans for unuploaded MKVs, scheduled via cron (`5 7 * * *`) or sleep-based timer.
- **youtube_upload_rs/** — Rust replacement for `youtube_upload.py`. Binary deployed as `~/youtube_upload`. Same functionality + appends to `~/upload_log.jsonl` + updates `timing.json`. Direct token refresh via Google OAuth2. Supports `--title` for custom upload titles (e.g. "Enhanced 4K v1" for brightness-corrected re-uploads). Built with `cargo build --release`, deployed via `deploy.sh update`.
- **tk_push_rs/** — TikTok video upload via Content Posting API. OAuth2 PKCE auth flow (`--auth`) with S256 hex-encoded SHA256 (TikTok deviates from RFC 7636 base64url). Local callback on port 8091, auto-kills stale listeners. Chunked upload (single chunk up to 64MB, 10MB for larger) with progress, status polling. Sandbox/unaudited apps must use `--privacy self` (uses inbox/draft endpoint). Usage: `tk_push --auth` (first time), `tk_push video.mp4 --title "Title" [--privacy self]`. Credentials in `tiktok_credentials.json`, token in `tiktok_token.json`. Writes PID to `~/tk_push.pid`.
- **create_short_rs/** — Rust binary `create_short` for extracting a segment from a YouTube video and re-uploading as a new video. Pipeline: yt-dlp `--download-sections "*START-END" --force-keyframes-at-cuts -f bestvideo[height<=2160]+bestaudio/best --merge-output-format mp4` → upload via Google YouTube API. Reuses auth/upload patterns from `youtube_upload_rs` (PythonToken refresh against `youtube_token.json`). Required: `--start`, `--end`, `--title`, `--description`. Optional: `--privacy {public|unlisted|private}` (default public), `--format`, `--output`, `--keep` (don't delete after upload), `--dry-run`. Default output `/tmp/create_short/<sanitized-title>_<start>-<end>.mp4`. Usage: `create_short <url-or-id> -s 12:44 -e 13:14 -t "title" -d "description"`. Run from project dir so `client_secret.json` + `youtube_token.json` are found. Description on the new video is auto-suffixed with `\n\nOriginal: <url> (<start>-<end>)` linking back to the source video.
- **create_shorts_gui/** — Cross-platform desktop GUI (eframe/egui) wrapping the same pipeline as `create_short` for non-CLI users (built so Jürg can self-serve). Form: YouTube URL/ID, start, end, title, description, privacy + **Preview button** (downloads the segment and opens it in the system default video player without uploading). Settings dialog (opened by clicking the app icon in the top-right) accepts a Google OAuth desktop client_id + client_secret (no shared client embedded — each user brings their own Google Cloud project / quota). One-time browser-based OAuth flow on `http://127.0.0.1:8093/`, refresh token persisted to platform config dir (`~/Library/Application Support/create_shorts/token.json` on macOS). Worker thread runs yt-dlp `--download-sections "*START-END" --force-keyframes-at-cuts` → resumable upload via Data API directly (no `google-youtube3` dep — direct `reqwest`), streaming progress to a log pane and progress bar. **Segment cache**: cut clips land at `<cache_dir>/create_shorts/segments/<video_id>_<start>_<end>.mp4` and are reused on identical re-requests (mostly the Preview→Upload flow). Note: 1.0.7 cached the *full source video* and 1.0.8 inherited that bug — extracting a 30-second clip from a one-hour 4K video pulled 4+ GiB. Reverted in 1.0.9 to per-segment downloads with exact-match caching. Optional `--cookies-from-browser` selector in settings for restricted content — `browsers.rs` probes the standard profile dirs on macOS/Linux/Windows for chrome/brave/chromium/edge/firefox/opera/safari/vivaldi, labels each detected entry as `<name> (installed)` in the dropdown, and on first launch auto-fills `cookies_browser` with the first detected browser. A "Test" button next to the dropdown shells out `yt-dlp --cookies-from-browser <name> --simulate --skip-download https://www.youtube.com/watch?v=jNQXAC9IVRw` (the never-deleted "Me at the zoo" URL) on a worker thread and reports ✅/❌ + the raw yt-dlp error so the user can tell "wrong browser" from "Safari keychain locked". Description gets the same `\n\nOriginal: <url> (<start>-<end>)` suffix the CLI uses. **Dependency check**: at startup probes `yt-dlp --version` / `ffmpeg -version` / `ffprobe -version` and shows a yellow warning banner if anything's missing; on macOS the banner has an "Install with Homebrew" button that shells out `brew install <missing>` in a worker thread (ffmpeg covers ffprobe), or "How to install Homebrew" + a copyable `/bin/bash -c "$(curl …)"` install command if brew isn't installed yet. **macOS PATH fix**: `ensure_homebrew_on_path()` prepends `/opt/homebrew/bin` + `/usr/local/bin` to PATH on startup so Finder-launched .apps actually find the Homebrew tools (Finder spawns with the system default PATH). **Log persistence**: every line is appended to `<config_dir>/log.txt` and re-loaded on startup (capped at 5000 lines); sessions are separated by `─── session started YYYY-MM-DD HH:MM:SS ───`. **Form persistence**: URL/start/end/title/description/privacy are saved via eframe's built-in storage (`App::save`) and restored on next launch so closing the app mid-edit doesn't lose work. **In-app update check**: on startup a worker hits `https://api.github.com/repos/zdavatz/old2new/releases`, finds the highest non-prerelease tag matching `create-shorts-vX.Y.Z`, and shows a blue banner if a newer version exists. The Settings dialog also has a manual "Check for updates" button reporting either the new version or "You're on the latest version (vX.Y.Z)". **In-app updater (1.0.10+, macOS only)**: when the running binary lives inside an `.app` bundle and the latest release exposes a `create_shorts-X.Y.Z-macos-universal.dmg` asset, the banner shows an "Update now" button (otherwise falls back to "Open release page"). Sparkle-style; doing the swap in-process risks "killed: 9" on relaunch when dyld notices the running executable was replaced. Pre-flight `check_writable_parent` aborts the download early if the .app's parent dir (typically `/Applications`) isn't writable, instead of wasting bandwidth. The helper-script `chmod 0755` call uses `std::os::unix::fs::PermissionsExt::set_mode` and is gated with `#[cfg(unix)]` since 1.0.12 — earlier 1.0.10/1.0.11 builds broke the Windows job (Windows release of 1.0.11 missing as a result). **Send via WhatsApp (1.0.11+)**: after a successful upload, the green success banner gets a `Send via WA` button that pushes `<title>\n<youtube-url>` to a configurable WhatsApp recipient. Self-contained — `whatsapp.rs` ships `send-text.mjs` + `login.mjs` + `package.json` via `include_str!` and the Settings dialog has a **Setup WhatsApp** button that writes them to `<config_dir>/whatsapp/` and runs `npm install --omit=dev --no-audit --no-fund` (deps: `@whiskeysockets/baileys`, `qrcode-terminal`, `pino`). **Link WhatsApp** button runs `login.mjs` and captures stdout — the script wraps the qrcode-terminal block with `QR-CODE-BEGIN`/`QR-CODE-END` markers and emits the literal `LINKED` sentinel on success so the GUI can show the QR in a modal (white frame, monospace black) and dismiss it on link. **1.0.14** ports the proven login flow from `~/software/pegelstand/whatsapp/login.mjs` after the in-house variant in 1.0.11–1.0.13 had the phone reject the device with "Gerät konnte nicht hinzugefügt werden" while terminal showed `LINKED`. The pegelstand pattern: declare success on the first `connection: open`, reconnect once on `close` with status 515 (DisconnectReason.restartRequired — normal post-pair restart), wipe + retry once on `close` with status 401/403 (stale session). Earlier attempts that gated success on `state.creds.me.id` or a post-pair second `open` were too clever and out of sync with what the WA server actually emits during pair. **1.0.15** fixes a critical persistence bug: Baileys' `creds.update` listener fires the `saveCreds` write asynchronously, and `process.exit(0)` after `LINKED` was racing with the disk flush — every successful link left `auth/creds.json` at 0 bytes, so the next process loaded an empty session and asked WhatsApp for a fresh QR (which then timed out with no `connection: open`). Login now chains saves into a tracked `lastSavePromise`, awaits the latest write + an explicit final `saveCreds()`, and polls `creds.json` size up to 3 s before exiting. **1.0.15** also adds a recipient picker: a 📞 **Browse** button in Settings spawns `list-recipients.mjs`, which calls `sock.groupFetchAllParticipating()` and emits `JID|TYPE|NAME` lines parsed by Rust into a modal list with a filter input. Group results are cached at `<wa-dir>/recipients.json` so subsequent opens are instant (with a small "refreshing" spinner while a background fetch updates the cache). The script retries up to 3× on any non-loggedOut close. 1:1 contacts are NOT enumerable from a saved-session connect — Baileys only pushes `messaging-history.set` / `contacts.upsert` during the *initial* QR-link phase, and `sock.resyncAppState(['regular_low','regular_high','regular','critical_unblock_low','critical_block'])` fires no events on a stable session (verified empirically). For 1:1 sharing, the success banner exposes a parados-style **Send to person…** button that opens `https://wa.me/?text=<title>%0A<url>` so WhatsApp's own UI handles contact selection — no Baileys round-trip, no recipient pre-config required. Auth lives at `<config_dir>/whatsapp/auth/` — a `creds.json` there means linked. ESM module resolution requires the script and `node_modules/` to be siblings, which is why we provision under config dir instead of pointing at pegelstand's `whatsapp/` (NODE_PATH/cwd doesn't help for ESM). Recipient is a phone number (digits, e.g. `41791234567`) or a group JID (`…@g.us`). Send: `node send-text.mjs <jid> <text>` with cwd = whatsapp dir; baileys reuses the saved session — no QR scan. Requires Node.js + npm in PATH; macOS users get them via Homebrew (current dep check probes yt-dlp/ffmpeg/ffprobe but not node — clear error message at send time if missing). Pegelstand is *not* required and *not* modified. Vendored `winit-patched/` removes winit's `_CGSSetWindowBackgroundBlurRadius` import (required for any future Mac App Store submission, harmless for plain notarization). Top bar follows the rust2xml convention — no app-name heading (OS title bar already shows it via `with_title`); right-aligned controls use `allocate_ui_with_layout(...)` so `with_layout(right_to_left)` actually flushes to the panel edge. The app icon itself is the click target for opening Settings (Sense::click() with a "Settings" hover tooltip). App icon at `assets/icon.png` (512×512 PNG, decoded to 64×64 `TextureHandle` lazily on first frame). **Cancel running job (1.0.35+)**: a red **✖ Cancel** button appears next to the action button while a job runs (one on the main form, one in the Upload modal) so a wrong start/end timestamp doesn't have to run to completion. Mechanism: each job gets a fresh `Arc<AtomicBool>` flag (`cancel` / `upload_cancel`, minted per job in `kick_off` / `start_direct_upload` so a prior Cancel can't abort the next run); the button does `flag.store(true)` and switches to a disabled "Cancelling…". In `pipeline.rs`, `wait_or_cancel(child, cancel)` **replaces every blocking `child.wait()`** — it polls the flag ~10×/s and kills the running yt-dlp/ffmpeg child the instant it flips (UI repaints every 150ms while running, so latency is ~250ms). All long-running spawn helpers (run_yt_dlp, download_tail_audio, download_section_audio, the repair-audio remux, apply_stretch/title_overlay/fade_in/fade_out) thread the flag through; `youtube::upload_video` checks it between 4 MB chunks and before the resumable-init POST. A new `Event::Cancelled` + `report_fail(tx, cancel, msg)` helper reports cancellation as a neutral "⏹ Cancelled" log line (resets progress, clears `running`) instead of a red error — `report_fail` keys on the flag, not the error text, so every stage reports uniformly despite its own prefix. **Process-group kill**: because `--download-sections --force-keyframes-at-cuts` makes yt-dlp drive **ffmpeg as a grandchild** to do the actual download/cut, a bare `child.kill()` would orphan that ffmpeg (it keeps downloading after "cancel"). So `detach_group(cmd)` calls `cmd.process_group(0)` (Unix, before spawn) to make each child its own group leader, and `kill_tree(child)` does `libc::kill(-pid, SIGKILL)` on the whole group **plus** `child.kill()` (belt-and-suspenders). `libc` is a `[target.'cfg(unix)'.dependencies]` (already transitive, so free); all `libc`/`CommandExt` use is `#[cfg(unix)]`-gated so the Windows build still compiles. `cleanup_partial_download` reaps yt-dlp's `.part`/`.fNNN.mp4`/`.fNNN.m4a` intermediates on the cancel/error path by globbing siblings whose name starts with `"<stem>."` (the trailing dot guards against nuking `<stem>_stretch5.mp4`-style derived caches). OAuth token refresh (`oauth.rs`) gained bounded `connect_timeout(10s)`/`timeout(30s)` and a pre-call cancel check so a stalled token endpoint right before upload can't hang the worker (which would leave Cancel stuck on "Cancelling…" with no child to kill); the YouTube client dropped from a 600s to a 120s per-request timeout + 15s connect_timeout so a stalled chunk surfaces within bounds. `drain_events` now detects `TryRecvError::Disconnected` (worker thread ended without a terminal event, i.e. panicked) and resets `running` + surfaces "worker exited unexpectedly" instead of leaving the UI stuck — the `if still_running` guard avoids a false positive on normal completion (crossbeam drains buffered messages before reporting Disconnected). **macOS hardware video path (1.0.36–1.0.39)**: every re-encode stage uses Apple's hardware H.264 encoder instead of CPU-bound libx264 — `video_encoder_args()` returns `h264_videotoolbox -q:v 65 -allow_sw 1 -pix_fmt yuv420p` on macOS (libx264 `-crf 20` elsewhere) for overlay/fade/stretch (1.0.36). The big win is the **segment cut itself (1.0.37–1.0.39)**: the old single yt-dlp `--download-sections --force-keyframes-at-cuts` forced a *software* VP9 decode + re-encode of the 4K source (~0.4–1.1× realtime, and it **thermally throttles** so the last 30% of a long cut crawls — worse in a hot room; the CPU pegs only ~4 cores because YouTube's VP9 decode caps at ~4 threads, the rest idle). 1.0.37 redirected yt-dlp's forced-keyframe re-encode onto videotoolbox via `--downloader-args ffmpeg_o:`, but that only moves the *encode* — the VP9 *decode* stayed software. **1.0.39 replaces the cut with a two-step on macOS** (`run()` else-branch + `hw_transcode_segment`): (1) `run_yt_dlp(..., stream_copy=true)` does a pure **stream copy** of the section (no re-encode, CPU-idle, download-bound) — empirically frame-accurate at the start even mid-GOP, so no boundary trim needed — to a `<id>_<stamp>.raw.mp4`; (2) the app's own ffmpeg `-hwaccel videotoolbox -hwaccel_output_format videotoolbox_vld -i raw -map 0:v:0 -map 0:a:0? -c:v h264_videotoolbox -q:v 65 -c:a aac` **hardware-decodes the VP9 and hardware-encodes H.264** at ~2× realtime, steady (no throttle), keeping full 4K. Falls back to software decode (still HW encode) if `-hwaccel` fails on the chip. Non-macOS keeps the single-step force-keyframes path. **Crash-safety**: the segment is built at a `<id>_<stamp>.partial.mp4` temp and `std::fs::rename`d onto the canonical `<id>_<stamp>.mp4` only on success (atomic, same dir), so `cached.exists()` is a valid-only signal — a SIGKILL/power-loss mid-build can't leave a truncated cache file that the next run reuses; the download branch also calls `cleanup_partial_download(&cached)` up front to sweep stale `.raw`/`.partial`/`.part` temps from a prior crash. Note: HW decode requires a videotoolbox-decodable source codec (VP9 on Apple Silicon); AV1-only sources would fall back to software. **yt-dlp auto-check (1.0.38)**: on launch `deps.yt_dlp_age_days()` parses the date-versioned `YYYY.MM.DD` and, if >30 days old (`YT_DLP_STALE_DAYS`), shows a yellow banner with a one-click **Update yt-dlp** button (`deps::yt_dlp_update_command()` → `brew upgrade yt-dlp` for Homebrew installs, else `yt-dlp -U`; streams to log, re-checks on done). Deliberately **not** auto-run on launch — a `brew upgrade` first triggers a heavy `brew update` (hundreds of git forks, load avg into the hundreds) that would freeze the machine and starve any running cut. **Cut out middle section(s) (1.0.43+, multi-range 1.0.44+)**: Form gets a *Cut out:* row — a "Remove middle section(s)" checkbox plus a list of *from* / *till* timestamp-field pairs (same style as start/end, absolute in the source video) with a ➕ **Add cut** button and a 🗑 per-row remove button (shown when >1 row). Form state holds `cut_middle: bool` + `cuts: Vec<CutRange{from,till}>` (fresh forms start with one empty row via `default_cuts()`). When ticked, `pipeline::apply_cut_middle` deletes every from/till range and concatenates everything that remains into one clip. Each cut's timestamps are converted to offsets from `start` and validated to lie strictly inside the segment (`0 < rel_from < rel_till < dur`, else a clear error); ranges are then sorted by start and overlaps rejected. The filter builds kept intervals `[0,c1_from) (c1_till,c2_from) … (cn_till,end]` — for each kept part i: `[0:v]trim=start=S:end=E,setpts=PTS-STARTPTS[vi];[0:a]atrim=start=S:end=E,asetpts=PTS-STARTPTS[ai]` (final part omits `:end=`), then `…concat=n=<K+1>:v=1:a=1[v][a]`, re-encoded via `video_encoder_args()` (hardware H.264 on macOS, libx264 elsewhere) + AAC. Applied **first** — before stretch, title, and fades — so every later stage operates on the joined clip and its shorter duration (downstream `segment_secs` is shadowed with the post-cut length). Cached as `<video_id>_<stamp>_cut<tag>.mp4` where `cuts_tag()` joins all ranges (`0_10_0_15-0_30_0_40`); the same `cut_tag` is folded into the stretch/titled cache filenames so toggling/changing cuts re-encodes rather than serving a stale derived clip. Applies to both Preview and Upload; upload cleanup removes the cut file too. **Export PDF of latest shorts (1.0.40+)**: a 📄 **PDF** button next to ⬆ Upload (and a headless `create_shorts_gui --export-pdf [path]` CLI flag handled in `main()` before the eframe window opens) writes a one-page A4 PDF of the `PDF_SHORTS_COUNT` (=10) latest shorts. **Preview-before-export (1.0.44+, select+full-history 1.0.45+)**: clicking 📄 PDF no longer exports directly — `start_pdf_fetch()` fetches the **full** shorts history via `shorts::all_rows()` (which calls `fetch_channel_latest(settings, None)` — same yt-dlp `--flat-playlist` call but with **no** `--playlist-end` cap; falls back to the complete `uploads.jsonl` history) on a worker (`pdf_fetching`/`pdf_fetch_rx`) and opens a **"Shorts for PDF"** modal (`draw_pdf_preview_modal`) listing every short (one movie per row: title, clickable URL, duration/meta) each with a **checkbox**, plus **Select all** / **Deselect all**, a "N of M selected" header, and **📄 Create PDF** / **Cancel**. `pdf_preview_selected: Vec<bool>` runs parallel to `pdf_preview_rows: Vec<PdfRow>` (now `#[derive(Clone)]`) and is auto-seeded so the **newest `PDF_SHORTS_COUNT` (=10)** are ticked by default (rows arrive newest-first); a length-mismatch guard resizes it each frame. ## Key Details

- Local: ncnn-vulkan uses Vulkan (Apple Silicon via MoltenVK). Cloud: ncnn-vulkan does NOT work in Docker (no Vulkan driver, falls back to CPU at 0.005 fps). **Always use PyTorch/CUDA for cloud.**
- Pre-flight validates: GPU CUDA arch, PyTorch/CUDA versions, CPU benchmark, RAM, disk + I/O, PCIe, ffmpeg, package versions.
- Pre-download disk check via `yt-dlp --dump-json` (no download) to estimate needs. Aborts if insufficient.
- CPU/disk impact: 4 vCPUs + 624 MB/s = 2.6 fps vs 16 vCPUs + 1207 MB/s NVMe = 7.0 fps (same RTX 4090). Always request 16+ vCPUs and NVMe >=1000 MB/s.
- CPU single-core matters: Xeon Phi 1.4GHz = 4x slower than EPYC 2.25GHz with same GPU. cv2.imread/imwrite bottlenecks on per-core speed.
- **RTX 5090 HD CPU benchmarks** (1920x1200, 2x, tile=512): Xeon Gold 6530 @ 0.9 GHz = ~0.1 fps (GPU idle!), Xeon 8481C @ 2.0 GHz = 0.3-0.4 fps, Ryzen 9 7950X @ 5.9 GHz = 0.5 fps, Threadripper PRO 7975WX @ 8.2 GHz = 0.5 fps, **Ryzen 9 9950X = 0.5 fps/GPU (best)**, Threadripper PRO 9975WX = 0.5 fps/GPU (slower than 9950X despite 64 cores — 4 CCDs = higher Infinity Fabric latency). Core count doesn't matter (16 cores sufficient), single-core speed + memory latency matters. **Min 3 GHz for RTX 5090 HD, ideal 5+ GHz.**
- RTX 5090 (Blackwell, sm_120) needs PyTorch 2.6+ / CUDA 12.8. Patch basicsr: `sed -i 's/functional_tensor/functional/' .../degradations.py`. Suppress tile spam: `sed -i "s/print(f'.*Tile/pass  # /" .../utils.py`. PyTorch 2.10 = no speedup over 2.7.

  - `ghcr.io/zdavatz/realesrgan-ncnn-vulkan:latest` — ncnn-vulkan (reference only, doesn't work on cloud)
  - Built from `nvidia/cuda:12.8.0-runtime-ubuntu24.04` (not `base` — base lacks CUDA runtime). Compat from `nvidia/cuda:12.1.1-runtime-ubuntu22.04`.
- Processing is resumable: checks existing output. **Fast resume**: existing frames → skip preflight/download/extraction → straight to upscaling.
- `realesrgan-x4plus` model for both 2x and 4x (general-purpose, best for real-world content)
- GFPGAN DISABLED — hallucinates facial features. Not suitable for documentary footage.
- Reassembly: libx264, CRF 18, `-preset medium`. **Auto brightness matching**: samples 10 frames, compares brightness, applies gamma correction. `-preset slow` abandoned (identical quality at CRF 18, YouTube re-encodes anyway, 2x slower).
- Parallel frame extraction (up to 16 ffmpeg workers).
- **Auto-tiling**: RTX 4090/5090 safe up to 1.6 MP without tiling. Above 1.6 MP → tile=512 (always, regardless of VRAM). L40S/A6000 (48GB) up to 2.0 MP, 80GB+ up to 4.0 MP. Tiling **faster** for high-res: 1920x1200 tile=512 = 0.56 fps vs no-tile = 0.13 fps (RealESRGAN processes at 4x internally). **Do NOT increase tile size** — larger tiles use more VRAM but are slower (see tile size benchmark).
- GPU power matters: RTX Pro 6000 Max-Q 300W = 0.44 fps, RTX 5090 575W = 0.56 fps, RTX Pro 6000 S 600W = 0.62 fps. Pre-flight warns <400W for >30GB VRAM.
- Two GPU profiles: **SD-4x** (RTX 4090, 24GB, ≤1.6 MP, 7.0 fps, $0.50/hr) and **HD-2x** (RTX 5090, 32GB, 0.5-1.7 fps, $0.69/hr).
- **Datacenter GPUs NOT suitable** (except GH200): RTX Pro 6000 S = 0.6 fps/$3.41, B200 = 0.57 fps/$3.13, H100 = 0.46 fps/$1.90, L40S = 0.3 fps, A100 = 0.07 fps. No-tile always slower than tile=512.
- **GH200 Grace Hopper FASTEST single-GPU**: 0.74 fps at $2.26/hr (RunCrate). ARM64 — no x86 Docker. Not cost-effective vs RTX 5090 ($0.30-0.76/hr at 0.51 fps).
- **Multi-GPU scales linearly**: 4x RTX 5090 = 1.47 fps combined ($1.35/hr). Each GPU runs own process via CUDA_VISIBLE_DEVICES.
- **Multi-GPU queue**: shared queue with `flock` for atomic access. Avoids batch-of-N anti-pattern (GPUs idle waiting for slowest).
- **OOM-Kill recovery**: exit code > 128 = signal → retry same video after 60s (not skip). Max 3 retries. Normal failures (exit 1) skip.
- **Resume worker monitor** (`resume_workers.sh`): checks every 30s, uses PID-files per GPU. Do NOT use `/proc/$pid/environ` (race condition).
- **Don't let ffmpeg block GPU**: start next video on free GPU while ffmpeg reassembles on another.
- **Disk estimates use peak, not sum**: `max(input, output)` because upscale.py deletes inputs during upscaling. Warns when single video >60% of total disk.
- **Resume-aware disk check**: accounts for existing frames on resume. Existing frames_in counted as reclaimable.
- **Clean already-upscaled frames_in**: on constrained disks, delete redundant frames_in with corresponding frames_out.
- **Multi-GPU segment splitting**: `enhance.sh` splits frames across GPUs, runs `upscale.py --start N --end M`. Linear speedup. Deploy: `./deploy.sh --multi-one [N] <video_id>`.
- **Dynamic GPU joining**: idle GPU auto-joins remaining video by taking tail segment.
- **Rebalance**: `./deploy.sh rebalance <instance_id>` redistributes frames across all GPUs. Runs via nohup.
- **Multi-GPU disk sizing**: 500GB / 4 GPUs = 125GB each. 1920x1200 2x: max ~5min/video. 960x720 2x: max ~17min.
- **yt-dlp JS challenge** (since ~March 2026): requires `--remote-components ejs:github` for deno JS solver. Without it: "This video is not available". Slim Docker image includes deno.
- **Watchdog**: checks every 60s if enhance_gpu.py is running, restarts if not (resumable).
- **RTX 5090 optimization**: tile=512 optimal, FP16 67% faster than FP32 (already used), tile_pad=0 = 7% but risks artifacts, torch.compile() incompatible. GPU draws only 208W/575W at 1920x1200 — framework/CPU-limited. Per-res fps: SD 640x480 = 3.27 fps (340W), HD 960x720 = 1.47 fps (281W), HD 1920x1200 = 0.44 fps (208W). **Tile size benchmark** (RTX 5090, 1920x1200 2x): tile=512 = 0.4 fps (6.5GB VRAM), tile=768 = 0.3 fps (22GB), tile=1024 = 0.2 fps (29.7GB). Larger tiles use more VRAM but are slower — 4x internal tensors exceed GPU L2 cache. **Do NOT try**: ONNX Runtime CUDA/TensorRT (fails on Blackwell sm_120, TRT recompiles engine per tile size), Python threading/prefetch (GIL blocks, slower than sequential), larger tiles (cache thrashing). Sequential Python tile=512 is the proven optimum — only multi-GPU scaling helps.
- **status_server_rs/** — Rust status server binary `~/status_server` (~1.5 MB). Auto-scans `~/jobs/` + `~/json/`. 7 phases: downloading, extracting, upscaling, assembling, uploading, paused, done. Per-phase progress with fps, frame counts, ffmpeg speed, upload %, download %. Reads titles from `json/{id}.json`. Endpoints: `/` (HTML), `/api/status` (JSON), `/compare/{title}`, `/frames/{title}/{dir}/{file}`, `/download/{title}`. **GLIBC**: cross-compiled binary needs glibc 2.39. Slim image works; compat image has pre-built binaries for glibc 2.35; older images need on-server build. `restart.sh` auto-falls back to Docker image binary (`/usr/local/bin/`) if deployed binary has glibc issues.
- **SSH nohup detach**: use `sudo bash -c "cd /root && nohup cmd >> log 2>&1 &"` — `bash -c` wrapper ensures proper detach from SSH session.
- Instance metadata in `~/instance_meta.json` (label, location, cost_per_hr, provider, instance_id) — shown in dashboard.
