# create_shorts_gui — architecture & version history

This file was split out of the root `old2new/CLAUDE.md` so it loads only
when working under `create_shorts_gui/` (keeps it out of unrelated
old2new sessions). The content below is the original bullet, verbatim.

- **create_shorts_gui/** — Cross-platform desktop GUI (eframe/egui) wrapping the same pipeline as `create_short` for non-CLI users (built so Jürg can self-serve). Form: YouTube URL/ID, start, end, title, description, privacy + **Preview button** (produces the clip without uploading and opens it in the system video player). **Split preview (1.0.48+, browser split-view 1.0.49+)**: Preview no longer opens a single file — it opens a **split view** so Jürg can compare the original against his edits: the **full original video** — embedded straight from YouTube (1.0.51+) so Jürg sees the whole, untrimmed source, not the downloaded start–end segment (which to him already counts as "cut") — on **top** and the **final edited clip** (`delivered`, a local `<video>`) **below**. The pipeline sends `Event::Preview { original, edited, source_id, start_secs }` (`source_id` = the YouTube id, `start_secs` deep-links the embed near the segment start; `original` = the raw start–end download, used as the top pane's fallback video). **Embed-failure fallback (1.0.52+)**: the top YouTube embed doesn't render on every machine — a content-blocker extension that eats `youtube.com/iframe_api`, an offline box, or a slow embed all leave the top pane **blank** ("no video opened"). So the embed pane now also carries a **hidden local `<video id="v1">`** of `original`, and the inlined JS reveals it (hides the iframe, `v.load()`, `wire('v1','tyt')`) whenever the embed can't come up: the IFrame API `onError`, the `iframe_api` `<script>` `onerror`, a `new YT.Player` throw, or a **6 s timeout** with no `onReady`. On fallback the top step buttons (`data-yt`) switch from `ytStep()` to `step('v1', …)` so they drive the local `<video>`; when the embed *does* load, nothing changes (full YouTube original, `ytStep`). Net: the top pane **always** shows a playing video with an **mm:ss** readout — the full original when the embed works, the downloaded original segment when it doesn't. When there's no embeddable id the pane is a plain local `<video>` from the start (`pane("1", …, "v1", "t1", …)`). **In-window mpv preview (1.0.53+, now the default)**: the whole browser split-page above is superseded when **libmpv** is available — Preview now plays the two clips **inside the app window** via `mpv.rs`, so there's no browser, no YouTube embed, no `_preview.html`/`preview_server`, and none of the embed-load fragility (Fehler 153, content-blockers) that 1.0.49–1.0.52 fought. `mpv.rs` **runtime-dlopens libmpv** (`libloading`, no build-time link → the app still builds/launches on all 3 platforms with mpv absent) and renders each frame with mpv's **software render API** (`MPV_RENDER_API_TYPE=sw`, params SW_SIZE=17/SW_FORMAT=18("rgb0")/SW_STRIDE=19/SW_POINTER=20 — verified against `mpv/render.h`) straight into an **RGBA byte buffer** handed to egui as a `TextureHandle` — **no** OpenGL interop and **no** native child surface, so the video is a normal egui image the app draws itself. That's the whole point vs a webview/VLC overlay (which egui can't paint on top of): the app **overlays the hand-entered cut ranges** — a slim seek **timeline** under each pane shades every cut red, plus a moving blue playhead, and a translucent **"✂ cut out"** banner flashes over the picture whenever the playhead enters a removed range. Each mpv `Player` (`open`→`mpv_create`+`mpv_initialize` with `hwdec=auto-copy`, `keep-open=yes`, `hr-seek=yes`, `config/load-scripts/osc=no`, then a `sw` render context + an update callback that flips an `AtomicBool` and calls `egui::Context::request_repaint` so playback is event-driven) exposes `poll_frame(w,h)` (renders only when there's a new frame / the pane resized / the dirty flag is set → then forces the rgb0 4th byte opaque), `set_paused`/`toggle_pause`/`seek_absolute`/`time_pos`/`duration`/`video_size` (reads `dwidth`/`dheight` to size the pane to the real aspect). `Event::Preview` builds a `PreviewState { orig, edited, …, cuts, seg_secs }` (cut ranges snapshotted as offsets from `start`, clamped to the segment) via `App::open_in_window_preview` and draws it in the central panel below the action buttons (`draw_preview`→`draw_video_pane`+`draw_timeline`, per-pane ▶/⏸ + mm:ss readout + click/drag seek, ✖ Close drops the players); when `original==edited` (no edits) it collapses to a single pane. If libmpv isn't loaded (or a player fails to open) it **falls back** to the old browser split view. macOS gets libmpv via `brew install mpv` (`libmpv.2.dylib`); Drop unhooks the callback before `mpv_render_context_free`/`mpv_terminate_destroy`. `drain_events` clones the `rx` `Receiver` so the Preview arm can take `&mut self` to open the players. **mpv-missing banner (1.0.54+)**: because the in-window preview is silent about *why* it fell back (only a log line), a machine without mpv (e.g. Jürg's) just saw Preview keep opening in the browser. So when `mpv_lib.is_none()` the form shows a blue info banner — "Preview opens in your browser because mpv isn't installed…" — with an **Install mpv with Homebrew** button (`start_mpv_install` → `brew install mpv` streamed to the log on a worker thread via the shared `BrewEvent` channel; on `Done`, `recheck_mpv()` re-dlopens libmpv so the preview lights up **without a restart**), a **Re-check** button, and a platform install hint (macOS `brew install mpv` / Windows `scoop install mpv` / Linux `apt install libmpv2`). mpv is treated as **optional** — it's *not* in `deps.missing()` (which blocks Preview/Upload for yt-dlp/ffmpeg/ffprobe), so its absence only downgrades Preview to the browser, never blocks. The `mpv_install_rx` drain clones the receiver (same reason as `drain_events`) so `recheck_mpv` can take `&mut self`. **HW-decode the re-encode stages (1.0.54+)**: a heavy Preview/Upload job (e.g. 6 cut ranges + title + fade on a 314 MB 4K segment) appeared to *hang* — the log froze at "Segment ready" with a macOS beachball and no progress. Root cause (measured): the cut filter (`apply_cut_middle`) **software-decoded the full ~260 s of 4K** (only the *encode* was hardware, via `video_encoder_args`), pegging ~2.5 CPU cores; on a slower/fewer-core Mac that starves the egui UI thread → beachball → the queued "Cutting out…" log + progress bar never draw. **Not** an mpv issue and **not** a `pipeline.rs` change (the mpv commit never touched it) — it's an old path that only shows up on unusually heavy jobs. Fix: `hwaccel_decode_args()` prepends `-hwaccel videotoolbox` (macOS) **before `-i`** on all four re-encode stages (`apply_cut_middle`, `apply_title_overlay`, `apply_fade_out`, `apply_fade_in`/`apply_stretch`), offloading the decode to the media engine and handing system-memory frames to the CPU filters. Measured on the 6-cut 4K repro: CPU drops from **92 s → 17.5 s** (≈5×) with **byte-identical output**, so the UI no longer starves (progress + logs stay live). Wall-clock trades off by CPU speed — on fast Apple Silicon the cut goes ~37 s→~69 s (media engine ~4× realtime vs multi-core software ~7×), but on a slower Mac HW decode is typically *faster* and, crucially, responsive. Falls back to software decode automatically if the codec isn't videotoolbox-decodable; empty (unchanged libx264 path) off macOS. The stream-copy remux (`repair_segment_audio`) and audio-only download don't decode video, so they're untouched. **mpv deadlock fix + no native window + split viewers (1.0.54):** the 1.0.53 in-window preview had two showstoppers found by sampling the hung process. (1) **Render-API deadlock**: `draw_video_pane` read time-pos/duration/dwidth/dheight via **blocking `mpv_get_property`** on the UI thread; while mpv's core thread inits the video output it blocks in a render rendezvous waiting for a render, so the blocking property call deadlocks (main waits for core, core waits for main → frozen). Fixed by reading those properties **asynchronously**: `mpv.rs` calls `mpv_observe_property` for each and runs a small **event-pump thread** (`mpv_wait_event` with a 0.1 s timeout so it notices the stop flag / can't block on the core dispatch lock) that caches the values in an `Arc<Mutex<Cached>>`; the UI thread only renders + reads the cache, never blocking. Drop stops+joins the event thread before `mpv_terminate_destroy`. (2) **mpv opened its OWN native window** (black in-app pane + stray window/dock-icon + Close hang) because inside an app with a live NSApplication mpv picks the platform VO (cocoa/gpu); forcing `vo=libmpv` (+ `force-window=no`) makes the software-render context the only VO. Both verified headlessly by process-sampling a demo (0 `mpv_get_property`/`mp_dispatch_lock` frames, 0 cocoa/GPU-VO frames, active `repack_*` sw-render frames). **Two separate in-window viewers now:** **👁 Load original** (`source_only` Job → `Event::SourceReady { path, start_secs: f64 }`, downloads just the start–end segment, no edits/repair) opens the raw segment in a **right `SidePanel`** beside the form (`draw_source_viewer`/`draw_source_pane`) with a big **absolute** "Source time" readout (`fmt_time_tenths`, segment offset + fractional start, so `9:47.5` reads exactly), the live cut overlay, and play/pause + frame-step + click-seek — for reading off cut-point timestamps while editing. **Preview** now shows the **edited clip ONLY** (single pane; `PreviewState` collapsed to one `player`+`tex`+`title`, `open_in_window_preview` opens just `edited`) since the original is watched separately. **Progress bar names the stage** (`stream_progress`/`emit_line` take a `phase` label: "Cutting out sections" / "Burning in title" / "Adding fade-out" / …) instead of a generic "Encoding segment". **HW-decode reverted**: `hwaccel_decode_args()` is now a no-op — the "hang" was the mpv deadlock, not CPU starvation, and software decode is faster on Apple Silicon (videotoolbox copy-back was ~2× slower wall-clock). `deps::brew_path()` is cached in `App.brew` (probed once at startup / on Re-check) because the mpv-missing + deps banners draw every frame and spawning `brew --version` 60×/s would stutter the UI. `CS_NO_MPV=1` forces the browser-preview fallback even when libmpv is present (for testing the no-mpv path). `open_split_preview()` in `main.rs` renders a tiny **self-contained HTML page** (top = a YouTube `<iframe>` embed, bottom = the local edited `<video controls>`). **Why HTML, not QuickTime (the 1.0.48 approach)**: QuickTime's position readout is a per-user **frame/timecode toggle** we can't script, and when macOS automation permission is off the AppleScript path fell back to whatever player the user set as default — so on Jürg's Mac the time read out as a **frame number** (e.g. `…F`) instead of mm:ss. HTML5 video controls **always** show the position as **mm:ss / mm:ss** on every machine (no toggle, no automation permission, no default-player surprises), and each pane keeps its own scrubber + **independent play/stop**. The page also renders its own big **mm:ss / mm:ss** readout per pane (`fmt()` + `wire()` in the inlined `<script>`, updated on `timeupdate`/`durationchange`). The page is written as `_preview.html` **in the segments cache dir** and served over **`http://127.0.0.1:<port>`** by a tiny built-in static server (`preview_server.rs` — started once, byte-serves with Range support so the local `<video>` scrubs in Safari), then opened at that URL — **not** as a `file://` URL, because YouTube's embedded player refuses a `file://` origin and fails with **"Fehler 153 (Konfiguration des Videoplayers)"**; over `http://127.0.0.1` (with a matching `&origin=` param) it loads. Each `<video src>` is the clip's percent-encoded **bare filename** resolved against the server root (`video_src()`; `path_to_file_url()` the absolute fallback). `build_preview_html()` uses `__CSS__`/`__BODY__` token replacement (not `format!`) so the JS braces survive. When **no edits** were applied `original == edited` and the page shows a single pane. Cross-platform (the old macOS-only `osascript`/`quicktime_split_script`/`applescript_quote` path is gone). **Subtitle-safe controls + frame stepping (1.0.50+)**: the browser's native `<video>` control bar sits at the bottom of the frame, right over the burned-in subtitles, so each pane **letterboxes a fixed ~48px black gutter** below the picture and the timeline lands in that gutter instead of over the subtitles. Because the panes are short/wide (the frame fills height, no natural letterbox), JS sizes each video on `loadedmetadata`/`resize` (`layout()`): it fits the frame into `availW × (availH−GUT)` preserving aspect, then sets the `<video>` element to `dispW × (dispH+GUT)` with `object-fit:contain; object-position:center top`, so the picture renders at the top and the GUT-px gutter is pure black at the bottom. Each pane's bar also gets **step buttons** — `−1s`, `−1f`, `+1f`, `+1s` — so Jürg can inch through the preview frame-by-frame (frame ≈ 0.04 s ≈ 25 fps). On the **bottom (local `<video>`) pane** they're `data-v`/`data-d` buttons wired to `step()` (pauses + nudges `currentTime`, clamped to `[0,duration]`). On the **top (YouTube) pane** the same buttons (1.0.51+) are `data-yt`/`data-d` and drive YouTube's **IFrame Player API** (`enablejsapi=1` on the embed; `ytStep()` pauses + `seekTo(currentTime±delta, true)`, `ytTick()` polls `getCurrentTime`/`getDuration` for the top pane's mm:ss readout) — the shared click handler routes to the player when `data-yt` is present, else to the `<video>`. Settings dialog (opened by clicking the app icon in the top-right) accepts a Google OAuth desktop client_id + client_secret (no shared client embedded — each user brings their own Google Cloud project / quota). One-time browser-based OAuth flow on `http://127.0.0.1:8093/`, refresh token persisted to platform config dir (`~/Library/Application Support/create_shorts/token.json` on macOS). Worker thread runs yt-dlp `--download-sections "*START-END" --force-keyframes-at-cuts` → resumable upload via Data API directly (no `google-youtube3` dep — direct `reqwest`), streaming progress to a log pane and progress bar. **Segment cache**: cut clips land at `<cache_dir>/create_shorts/segments/<video_id>_<start>_<end>.mp4` and are reused on identical re-requests (mostly the Preview→Upload flow). Note: 1.0.7 cached the *full source video* and 1.0.8 inherited that bug — extracting a 30-second clip from a one-hour 4K video pulled 4+ GiB. Reverted in 1.0.9 to per-segment downloads with exact-match caching. Optional `--cookies-from-browser` selector in settings for restricted content — `browsers.rs` probes the standard profile dirs on macOS/Linux/Windows for chrome/brave/chromium/edge/firefox/opera/safari/vivaldi, labels each detected entry as `<name> (installed)` in the dropdown, and on first launch auto-fills `cookies_browser` with the first detected browser. A "Test" button next to the dropdown shells out `yt-dlp --cookies-from-browser <name> --simulate --skip-download https://www.youtube.com/watch?v=jNQXAC9IVRw` (the never-deleted "Me at the zoo" URL) on a worker thread and reports ✅/❌ + the raw yt-dlp error so the user can tell "wrong browser" from "Safari keychain locked". Description gets the same `\n\nOriginal: <url> (<start>-<end>)` suffix the CLI uses. **Dependency check**: at startup probes `yt-dlp --version` / `ffmpeg -version` / `ffprobe -version` and shows a yellow warning banner if anything's missing; on macOS the banner has an "Install with Homebrew" button that shells out `brew install <missing>` in a worker thread (ffmpeg covers ffprobe), or "How to install Homebrew" + a copyable `/bin/bash -c "$(curl …)"` install command if brew isn't installed yet. **macOS PATH fix**: `ensure_homebrew_on_path()` prepends `/opt/homebrew/bin` + `/usr/local/bin` to PATH on startup so Finder-launched .apps actually find the Homebrew tools (Finder spawns with the system default PATH). **Log persistence**: every line is appended to `<config_dir>/log.txt` and re-loaded on startup (capped at 5000 lines); sessions are separated by `─── session started YYYY-MM-DD HH:MM:SS ───`. **Form persistence**: URL/start/end/title/description/privacy are saved via eframe's built-in storage (`App::save`) and restored on next launch so closing the app mid-edit doesn't lose work. **In-app update check**: on startup a worker hits `https://api.github.com/repos/zdavatz/old2new/releases`, finds the highest non-prerelease tag matching `create-shorts-vX.Y.Z`, and shows a blue banner if a newer version exists. The Settings dialog also has a manual "Check for updates" button reporting either the new version or "You're on the latest version (vX.Y.Z)". **In-app updater (1.0.10+, macOS only)**: when the running binary lives inside an `.app` bundle and the latest release exposes a `create_shorts-X.Y.Z-macos-universal.dmg` asset, the banner shows an "Update now" button (otherwise falls back to "Open release page"). Click → `installer.rs` downloads the notarized DMG to a tmp dir with live progress bar (`Downloading update`, MB / MB), `hdiutil attach -nobrowse -readonly`, runs `codesign --verify --deep --strict` on the new `.app` (refuses to install an unsigned bundle), `ditto`s the new `.app` to a sibling staging path (`.create_shorts.app.new.<pid>`), detaches the DMG, writes a tiny bash helper to `/tmp/create_shorts_install_<pid>.sh` that polls `kill -0 <pid>` until this process dies, then `mv`s current → `.bak.<pid>`, `mv`s staging → current, removes the backup, `open`s the new bundle and self-deletes. The GUI sleeps 600 ms after `Done` so the user reads "Update staged. Restarting…" and then `process::exit(0)`s — the helper finishes the swap once we're gone. Sparkle-style; doing the swap in-process risks "killed: 9" on relaunch when dyld notices the running executable was replaced. Pre-flight `check_writable_parent` aborts the download early if the .app's parent dir (typically `/Applications`) isn't writable, instead of wasting bandwidth. The helper-script `chmod 0755` call uses `std::os::unix::fs::PermissionsExt::set_mode` and is gated with `#[cfg(unix)]` since 1.0.12 — earlier 1.0.10/1.0.11 builds broke the Windows job (Windows release of 1.0.11 missing as a result). **Send via WhatsApp (1.0.11+)**: after a successful upload, the green success banner gets a `Send via WA` button that pushes `<title>\n<youtube-url>` to a configurable WhatsApp recipient. Self-contained — `whatsapp.rs` ships `send-text.mjs` + `login.mjs` + `package.json` via `include_str!` and the Settings dialog has a **Setup WhatsApp** button that writes them to `<config_dir>/whatsapp/` and runs `npm install --omit=dev --no-audit --no-fund` (deps: `@whiskeysockets/baileys`, `qrcode-terminal`, `pino`). **Link WhatsApp** button runs `login.mjs` and captures stdout — the script wraps the qrcode-terminal block with `QR-CODE-BEGIN`/`QR-CODE-END` markers and emits the literal `LINKED` sentinel on success so the GUI can show the QR in a modal (white frame, monospace black) and dismiss it on link. **1.0.14** ports the proven login flow from `~/software/pegelstand/whatsapp/login.mjs` after the in-house variant in 1.0.11–1.0.13 had the phone reject the device with "Gerät konnte nicht hinzugefügt werden" while terminal showed `LINKED`. The pegelstand pattern: declare success on the first `connection: open`, reconnect once on `close` with status 515 (DisconnectReason.restartRequired — normal post-pair restart), wipe + retry once on `close` with status 401/403 (stale session). Earlier attempts that gated success on `state.creds.me.id` or a post-pair second `open` were too clever and out of sync with what the WA server actually emits during pair. **1.0.15** fixes a critical persistence bug: Baileys' `creds.update` listener fires the `saveCreds` write asynchronously, and `process.exit(0)` after `LINKED` was racing with the disk flush — every successful link left `auth/creds.json` at 0 bytes, so the next process loaded an empty session and asked WhatsApp for a fresh QR (which then timed out with no `connection: open`). Login now chains saves into a tracked `lastSavePromise`, awaits the latest write + an explicit final `saveCreds()`, and polls `creds.json` size up to 3 s before exiting. **1.0.15** also adds a recipient picker: a 📞 **Browse** button in Settings spawns `list-recipients.mjs`, which calls `sock.groupFetchAllParticipating()` and emits `JID|TYPE|NAME` lines parsed by Rust into a modal list with a filter input. Group results are cached at `<wa-dir>/recipients.json` so subsequent opens are instant (with a small "refreshing" spinner while a background fetch updates the cache). The script retries up to 3× on any non-loggedOut close. 1:1 contacts are NOT enumerable from a saved-session connect — Baileys only pushes `messaging-history.set` / `contacts.upsert` during the *initial* QR-link phase, and `sock.resyncAppState(['regular_low','regular_high','regular','critical_unblock_low','critical_block'])` fires no events on a stable session (verified empirically). For 1:1 sharing, the success banner exposes a parados-style **Send to person…** button that opens `https://wa.me/?text=<title>%0A<url>` so WhatsApp's own UI handles contact selection — no Baileys round-trip, no recipient pre-config required. Auth lives at `<config_dir>/whatsapp/auth/` — a `creds.json` there means linked. ESM module resolution requires the script and `node_modules/` to be siblings, which is why we provision under config dir instead of pointing at pegelstand's `whatsapp/` (NODE_PATH/cwd doesn't help for ESM). Recipient is a phone number (digits, e.g. `41791234567`) or a group JID (`…@g.us`). Send: `node send-text.mjs <jid> <text>` with cwd = whatsapp dir; baileys reuses the saved session — no QR scan. Requires Node.js + npm in PATH; macOS users get them via Homebrew (current dep check probes yt-dlp/ffmpeg/ffprobe but not node — clear error message at send time if missing). Pegelstand is *not* required and *not* modified. Vendored `winit-patched/` removes winit's `_CGSSetWindowBackgroundBlurRadius` import (required for any future Mac App Store submission, harmless for plain notarization). Top bar follows the rust2xml convention — no app-name heading (OS title bar already shows it via `with_title`); right-aligned controls use `allocate_ui_with_layout(...)` so `with_layout(right_to_left)` actually flushes to the panel edge. The app icon itself is the click target for opening Settings (Sense::click() with a "Settings" hover tooltip). App icon at `assets/icon.png` (512×512 PNG, decoded to 64×64 `TextureHandle` lazily on first frame). **Cancel running job (1.0.35+)**: a red **✖ Cancel** button appears next to the action button while a job runs (one on the main form, one in the Upload modal) so a wrong start/end timestamp doesn't have to run to completion. Mechanism: each job gets a fresh `Arc<AtomicBool>` flag (`cancel` / `upload_cancel`, minted per job in `kick_off` / `start_direct_upload` so a prior Cancel can't abort the next run); the button does `flag.store(true)` and switches to a disabled "Cancelling…". In `pipeline.rs`, `wait_or_cancel(child, cancel)` **replaces every blocking `child.wait()`** — it polls the flag ~10×/s and kills the running yt-dlp/ffmpeg child the instant it flips (UI repaints every 150ms while running, so latency is ~250ms). All long-running spawn helpers (run_yt_dlp, download_tail_audio, download_section_audio, the repair-audio remux, apply_stretch/title_overlay/fade_in/fade_out) thread the flag through; `youtube::upload_video` checks it between 4 MB chunks and before the resumable-init POST. A new `Event::Cancelled` + `report_fail(tx, cancel, msg)` helper reports cancellation as a neutral "⏹ Cancelled" log line (resets progress, clears `running`) instead of a red error — `report_fail` keys on the flag, not the error text, so every stage reports uniformly despite its own prefix. **Process-group kill**: because `--download-sections --force-keyframes-at-cuts` makes yt-dlp drive **ffmpeg as a grandchild** to do the actual download/cut, a bare `child.kill()` would orphan that ffmpeg (it keeps downloading after "cancel"). So `detach_group(cmd)` calls `cmd.process_group(0)` (Unix, before spawn) to make each child its own group leader, and `kill_tree(child)` does `libc::kill(-pid, SIGKILL)` on the whole group **plus** `child.kill()` (belt-and-suspenders). `libc` is a `[target.'cfg(unix)'.dependencies]` (already transitive, so free); all `libc`/`CommandExt` use is `#[cfg(unix)]`-gated so the Windows build still compiles. `cleanup_partial_download` reaps yt-dlp's `.part`/`.fNNN.mp4`/`.fNNN.m4a` intermediates on the cancel/error path by globbing siblings whose name starts with `"<stem>."` (the trailing dot guards against nuking `<stem>_stretch5.mp4`-style derived caches). OAuth token refresh (`oauth.rs`) gained bounded `connect_timeout(10s)`/`timeout(30s)` and a pre-call cancel check so a stalled token endpoint right before upload can't hang the worker (which would leave Cancel stuck on "Cancelling…" with no child to kill); the YouTube client dropped from a 600s to a 120s per-request timeout + 15s connect_timeout so a stalled chunk surfaces within bounds. `drain_events` now detects `TryRecvError::Disconnected` (worker thread ended without a terminal event, i.e. panicked) and resets `running` + surfaces "worker exited unexpectedly" instead of leaving the UI stuck — the `if still_running` guard avoids a false positive on normal completion (crossbeam drains buffered messages before reporting Disconnected). **macOS hardware video path (1.0.36–1.0.39)**: every re-encode stage uses Apple's hardware H.264 encoder instead of CPU-bound libx264 — `video_encoder_args()` returns `h264_videotoolbox -q:v 65 -allow_sw 1 -pix_fmt yuv420p` on macOS (libx264 `-crf 20` elsewhere) for overlay/fade/stretch (1.0.36). The big win is the **segment cut itself (1.0.37–1.0.39)**: the old single yt-dlp `--download-sections --force-keyframes-at-cuts` forced a *software* VP9 decode + re-encode of the 4K source (~0.4–1.1× realtime, and it **thermally throttles** so the last 30% of a long cut crawls — worse in a hot room; the CPU pegs only ~4 cores because YouTube's VP9 decode caps at ~4 threads, the rest idle). 1.0.37 redirected yt-dlp's forced-keyframe re-encode onto videotoolbox via `--downloader-args ffmpeg_o:`, but that only moves the *encode* — the VP9 *decode* stayed software. **1.0.39 replaces the cut with a two-step on macOS** (`run()` else-branch + `hw_transcode_segment`): (1) `run_yt_dlp(..., stream_copy=true)` does a pure **stream copy** of the section (no re-encode, CPU-idle, download-bound) — empirically frame-accurate at the start even mid-GOP, so no boundary trim needed — to a `<id>_<stamp>.raw.mp4`; (2) the app's own ffmpeg `-hwaccel videotoolbox -hwaccel_output_format videotoolbox_vld -i raw -map 0:v:0 -map 0:a:0? -c:v h264_videotoolbox -q:v 65 -c:a aac` **hardware-decodes the VP9 and hardware-encodes H.264** at ~2× realtime, steady (no throttle), keeping full 4K. Falls back to software decode (still HW encode) if `-hwaccel` fails on the chip. Tick rate 100 ms while the bar shows. **⏪ backwards**: a checkbox after the volume field (`FormState.bg_music_reverse` → `Job.bg_music_reverse`, serde default false) plays the music **back-to-front — in the audition AND mixed into the clip**, so what you hear on Play is what lands in the video. Implementation: the track is reversed into a cached copy first — `pipeline::build_reversed_music` runs `ffmpeg -i src -vn -af areverse -c:a aac -b:a 192k` (`-vn` drops mp3 cover-art streams) into `<segments-dir>/music_rev_<music_file_tag>.m4a` via the `.partial` + rename crash-safety pattern — because `areverse` needs the whole track before it emits a sample, so it **cannot** sit inside the looped `apply_bg_music` graph (`-stream_loop -1` never EOFs → the filter would buffer forever). The cache is keyed by the original file's path/size/mtime, so the GUI audition and the pipeline build/reuse the **same** file. Pipeline: when `bg_music_reverse`, the mix-stage input swaps to the reversed copy and the mix cache name gains an `r` marker (`_music<tag>r_v<vol>`) so toggling the direction re-mixes instead of serving a stale clip; `music_file_tag` still hashes the original. GUI: Play with ⏪ ticked builds the copy on a worker thread (~1–3 s — blocking the UI would beachball; button shows a disabled "⏳ Reversing…", result arrives via `music_rev_rx: Option<Receiver<Result<PathBuf,String>>>` polled in the row), then auditions it through the shared `start_music_audition` helper (extracted from the old inline mpv-open; falls back to the system player without libmpv — which then also gets the reversed file). Toggling the checkbox, picking a new file, or unticking Add-background-music stops the audition and abandons a pending build. Verified with real ffmpeg: a loud-then-quiet test file reverses to quiet-then-loud (−21.5/−91 dB → −91/−21.6 dB), duration preserved.
